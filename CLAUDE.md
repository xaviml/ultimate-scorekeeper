# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Yarn is the package manager (CI runs `yarn install --frozen-lockfile`; a stale `package-lock.json` is also present — prefer `yarn.lock`).

```bash
yarn dev                              # Vite dev server on :5173
yarn build                            # tsc -b && vite build → dist/
yarn test                             # vitest run
yarn test:watch
yarn lint                             # eslint src --ext .ts,.tsx
yarn format                           # prettier --write src/**

yarn vitest run src/__tests__/gameReducer.test.ts       # single file
yarn vitest run -t "blocks scoring before the pull"     # single test by name
```

CI (`.github/workflows/deploy.yml`) runs lint → test → build on PRs and on `main`, then deploys `dist/` to GitHub Pages. The Pages build sets `GITHUB_PAGES=true`, which switches Vite `base` to `/ultimate-scorekeeper/`; rename the repo and you must update `vite.config.ts`.

## Architecture

A single-page PWA with **no router and no server**. `src/App.tsx` switches screens purely off `state.phase` (`config` → `game` → `report`).

### The reducer is the whole domain model

`src/state/gameReducer.ts` (~580 lines) holds every Ultimate rule: score validation, gender ratio, caps, half-time, timeouts, undo. It is pure and synchronously testable — `src/__tests__/gameReducer.test.ts` drives it by folding action arrays over `createInitialState()`. **New game rules go in the reducer with tests, never in components.** Components only read state and dispatch.

Guard functions are exported alongside the reducer and reused by the UI to decide what to disable or explain: `canScore`, `canUndo`, `timeoutAvailability`, `pullFromSide`, `leftEndzoneTeam`. Each returns `{ ok, reason? }`, and `reason` is an i18n key suffix (see below) — so a new rejection path needs a matching translation in both dictionaries.

Things that are easy to get wrong and are already decided in the reducer:

- **Undo** pushes a `GoalSnapshot` per goal. `points` is deliberately _not_ in the snapshot: a goal appends exactly one `PointRecord`, so undo slices the last one off. Don't "fix" this by storing the array — it makes the payload grow quadratically.
- **A turnover is undone by long-pressing Turn, and needs no snapshot.** `UNDO_TURNOVER` just flips `possessionTeam` back, because a point starts with the receiving team and every turnover since is unwound in reverse order. What it does need is `pointTurnovers` (reset by `PULL_THROWN`/`GOAL`, restored from `GoalSnapshot` by `UNDO_GOAL`): without it, a long-press on a point where nothing was turned over would hand the disc away from the team that received the pull. The log side follows `UNDO_GOAL` exactly — the entry is dropped when the turnover is still the last thing logged, and an `undoTurnover` correction entry is written once something else has been recorded since. **Possession is shown as a rule, not a chip**, and it is derived, not stored: `possessionTracked` (`statsMode !== 'none'`) decides whether it is drawn at all, and `possessionTeam !== null` whether anything is lit right now. It is a 4 px track (3 px landscape) between the score panels and the action row, with the holder's half filled in `signal` — position rather than words, since the panels keep a fixed side all game and the chip it replaced spelled out a name already on screen in 52 px letters. Three things about it are deliberate: the 1 px `line` hairline above it is the border the action row used to draw, **moved up rather than added** (so the whole thing costs 4 px, and the action row's own `border-t` is conditional on the rule being there), and it is also what keeps the amber legible against a team that picked yellow — down there the fill only meets a team colour along that one edge, which is why no ring around the bar is needed. The fill is _mounted_ only while the disc is live rather than faded in place, because that is what makes the motion read correctly: inside a point the element persists so a turnover slides it across, and between points it unmounts so the next point's fill appears in place instead of gliding in from the side that just lost it. And it carries no wording at all — the old `possessionChip` key is gone from the dictionaries; tests read the `data-possession` attribute the strip exposes for that reason. One happy accident worth not breaking: `possessionTeam` is `null` for exactly the window the amber "Pull thrown" button occupies, so the two ambers are never lit at once.
- **Scoreboard side ≠ physical side.** The scoreboard keeps each team on a fixed side all game; `leftEndzoneTeam`/`pullFromSide` track the real ends, which swap every point and mirror at half-time.
- **The game clock keeps running during timeouts and half-time.** Only `paused` (manual pause, SOTG stoppage, or a `STOPPAGE` left unresolved for `PROLONGED_STOPPAGE_SECONDS`) stops it. An injury/technical stoppage is logged without touching the clock at first — `pendingStoppage.elapsedSeconds` ticks forward every `TICK` regardless, and once it hits two minutes unresolved the reducer auto-pauses (`statusBeforePause` set, same shape as SOTG) so a lingering stoppage doesn't quietly eat into game time. From there "Resume game" (`STOPPAGE_RESOLVED`, not `SOTG_TOGGLE`) both un-pauses and resolves the stoppage in one action — the small "Play can resume" button (`StoppageResolutionRow`) hides itself once `clockStopped` is true, in favour of the same action-row button SOTG uses.
- **A stoppage interrupts everything else, and everything else waits where it was.** Injury, technical and SOTG/manual-pause share one guard, `canStoppage`, which is open for the whole game — between points, during a timeout or half-time, over an unresolved call — and closes only before the game starts, after it finishes, and while another stoppage is already open (`reason: 'stoppageInProgress'`; the raised-hand button stays tappable and flashes it rather than going dead). `playHalted` (`pendingStoppage !== null || status === 'paused'`) is what the rest of `TICK` consults: the pull clock, a running timeout, the half-time break and `pendingCall.elapsedSeconds` all stop advancing and pick up from the exact value they froze at. A pause would freeze `secondary` for free by leaving the status it ticks under — a stoppage does not touch status, which is why the check is explicit. `PULL_THROWN`, `TIMEOUT_END` and `HALFTIME_END` are refused while a stoppage is open (their buttons fade), and `timeoutAvailability` refuses a new timeout, so nothing advances play past the thing that stopped it. Only `pendingStoppage.elapsedSeconds` and the game clock ignore `playHalted` — the stoppage is what's being waited on, and a plain stoppage was never meant to stop game time before the two-minute rule.
- **`statusBeforePause` and `statusBeforeTimeout` are two fields on purpose.** A pause can now happen _during_ a timeout, so one field could not carry both ways back: the pause remembers `'timeout'`, while the timeout still remembers whether it was called before or after the pull (which decides the WFDF restart in `TIMEOUT_END`).
- **Half-time can only trigger on a goal**, never mid-point — the in-progress point always plays out.
- **A water break is the one break that never ends by itself.** Hot-weather hydration breaks (WFDF Appendix B4.3) are `status: 'waterBreak'` with a `secondary` of kind `waterBreak` that counts **up** — unlike a timeout or half-time, which count down and are auto-ended by `GameContext` at 0. Reaching `total` only turns the clock amber, swaps the ambient line to `now_waterBreakDue` and fires the `waterBreakDue` call-out once (in `TICK`, on the crossing); the teams come back when they come back, and the amber action-row button (`WATER_BREAK_END`, styled like "Pull thrown" because it is the only way out) is what ends it — always back to `awaitingPull` with the pull clock restarted, since a break only ever happens in that gap and nothing about the point order moves on. Automatic breaks fire inside `GOAL` off `config.waterBreaks.atScores`, read against the **leading** score ("when the first team reaches N"), resolved after the game-over and half checks so neither can be pre-empted — half-time swallows a break due on the same goal and `waterBreaksTaken` records it as spent either way. `WATER_BREAK_START` (manual, from `StoppageDialog`) spends everything already due for the same reason: otherwise the automatic one fires on the very next goal, right after the teams finished drinking. It is the one entry in that dialog **not** guarded by `canStoppage` — `canWaterBreak` is narrower, not wider (`awaitingPull` only), because the rule puts hydration breaks in the transitions. Both the timer and the game clock behave like half-time's: frozen by `playHalted`, and the game clock keeps running. Timeouts need no rule of their own — `timeoutAvailability` already refuses on any status that isn't `live`/`awaitingPull`, which is exactly the "a water break costs neither team a timeout" the protocol requires.
- Conditional end cap (Option C) is resolved inside `GOAL`, not when the time cap fires, because it depends on the score difference _after_ the point finishes.
- **A capped target is editable by hand, because the horn's timing against a goal is not something the app can know.** The horn is on the clock but the goal is on the volunteer's thumb: a goal scored a breath before the horn and tapped in a breath after it (or the reverse) moves the target by exactly one, and no guard can catch that — the reducer's view of the timing _is_ the typing speed. So `capTargetOptions(state, 'game' | 'half')` keeps the number open over the values it could legitimately take, and `SET_CAP_TARGET` writes one. Three things hold it together: the offered list **is** the guard (the action refuses anything not in it, so the bounds live in one place); writing the target **is** the resolution, because `GOAL` only resolves a cap whose target is still `null`, so a hand-named number is what the next goal reads rather than something it overwrites; and the pick is **silent** — the cap was announced and whistled when it landed, and this is the volunteer fixing which point it landed in, not a second cap for the players to hear about (the same reasoning as `EDIT_LOG_ENTRY`). Silence still has to be written: `assist` is set to `capTargetSet`, a key deliberately absent from `SAY`, `SIGNAL` and `currentWhistle`'s cap list, because the occurrence key carries `nextLogId` and the log entry has just moved it — leaving the previous assist in place would re-announce _that_ instead. Undo needs nothing new — `snapshot()` already carries both capped targets, so an override goes back with the goal it was named over. The options are `leader + plus` and one more while the cap is pending (both named on the chip, "Half at 5 or 6" — telling the volunteer to wait for a number the game may already have decided is the bug this fixes), and the resolved value ±1 afterwards, always floored at `leader + 1` (a target already reached is not a target) and capped at the configured score, the half additionally held below `effectiveTarget`. It deliberately does **not** consult `halfTargetApplies` wholesale: while a half cap is pending that helper reads the _configured_ half score, which is the number about to be lowered, so it retires the half one goal before the cap resolves it back into reach. Option A (`none`) is never offered — there is no number — and Option C only once resolved, since before that one of its outcomes is "the game is already over", which a list of targets cannot say.
- **The cap chip is the control, and the `now_*` line is what says so.** `CapChip` in `GameScreen` renders both targets and is a `<button>` only while `capTargetOptions` offers a choice — where the bounds leave one number it is the plain label it always was, so the dialog never asks a question with one answer. It is the one thing over the score panels that takes a tap (`SignalCard` is `pointer-events-none` precisely so it can't), which is why it stays small and on the seam between the panels, where a scoring tap is ambiguous anyway. The bar carries the hint on `now_awaitingPullCap`/`now_discInPlayCap` — the two statuses that span the whole window the tap works in — and rides on them rather than overriding anything above in `statusKey`: the pull whistles and the universe point are about seconds passing, and a target can wait for them.
- **Recorded events are bookkeeping only** — they never touch the score, clock or possession, only the log and the assist hint. They share one guard, `canRecordEvent`, with two opt-in modifiers. Base: looser than `canScore` in one respect (an SOTG pause doesn't block it — a foul called as the teams line up is still a foul), but a timeout or half-time is a break in play, so recording waits for the game to resume, same as scoring does; it also blocks before the game starts and after it finishes. `requiresPull` narrows it to things that need a live disc (travel, the seven calls). Stoppages are **not** guarded by this at all — see `canStoppage` above. `allowDuringBreaks` widens it past the timeout/half-time block, and **only `NOTE` passes it** — a note isn't about the play, and a break is precisely when a volunteer has a free hand to write one. Since a note is written from the log dialog, which stays open through a timeout, refusing it there silently swallowed what had just been typed.

One consequence worth knowing: a note recorded between a goal and an undo of that goal pushes `UNDO_GOAL` off its clean-removal path onto the visible-correction path (see the `goalLog.type === 'goal'` check). That's the designed fallback for "something was logged in between", and a timeout called after a goal already triggered it — the note just makes it reachable during half-time too. They are reached from **four different places**, split by what the volunteer is doing rather than by the fact that they all end up in the log — the grouping the old single "Record event" dialog used, which put a turnover and an SOTG stoppage side by side. Now: the seven calls and travel sit behind the **Call** button (`CallDialog`, a shout bubble — deliberately not a whistle, since Ultimate is self-refereed and a whistle already means the clock talking); injury, technical and SOTG sit behind the **raised hand** (`StoppageDialog`); a turnover has its own **Turn** button; and a free-text note is written from the header of the log dialog itself, which is where what it writes ends up. The kinds: `TRAVEL` (team attributed via `TravelTeamDialog`, but never a player — a travel is called on the thrower by the marker, and chasing down which player it was is more than a volunteer can follow; it registers in one step, with no `pendingCall` and no resolution), `NOTE` (free text — the only recorded event with no call-out and no signal), and the seven player calls via `CALL_MADE`/`CALL_RESOLVED`. A call opens `state.pendingCall` (one at a time — the resolution buttons answer exactly one question) and `CALL_RESOLVED` logs `pendingCall.elapsedSeconds` — a counter independent of the game clock (a timeout doesn't stall a dispute) but frozen by `playHalted`, so a stoppage or an SOTG pause raised mid-dispute isn't counted against the players. It is also exactly what the secondary clock box displays, which is why the two can't drift. The three resolution buttons render while `pendingCall` is set **and play is not halted** — a stoppage or an SOTG pause raised mid-discussion takes the row away and leaves only its own resolve button, since the discussion is frozen and one question at a time is the point of that row. `CALL_RESOLVED` carries the same `playHalted` guard so the rule doesn't live only in the component; the call stays open and is answered untouched once play resumes. **They render into the action row's reserved slot** — the one "Pull thrown" and "End timeout" occupy — because answering a call is the one thing that moves play on while one is open, and because that slot is provably free for exactly this window rather than coincidentally free: `actionRowStatus` is null only for `live`, `CALL_MADE` needs a live disc (`requiresPull`), and `canScore`/`timeoutAvailability` both refuse while `pendingCall` is set, so the status cannot leave `live` underneath an open call. The only thing that can happen over one is a stoppage or a pause, which is exactly what `playHalted` already takes the row away for. A test pins each occupied status against `CALL_MADE` being refused there, since that is the invariant a new rule could break. The row carries **no heading naming the call** (the amber ambient line is already saying "{kind} called by {team} … tap Accepted, Contested or Retracted", the old `callPending`/`callPendingNoTeam` keys are gone) — a label would push it past the reserved height and start resizing the score panels above, which is the one thing that height exists to prevent. `StoppageResolutionRow` deliberately does **not** follow it there: a stoppage can be raised between points, during a timeout, half-time or a water break, where the slot already holds that break's own faded button, so above the clocks stays the one place free in every status it can be open in.

- **`config.trackPlayers`, labelled "Track game activity" in the UI, is one stats toggle that now gates all of the above's attribution, not just per-player detail.** Off (the default): Roster and Turn don't appear in the action row at all — there's no way to log a turnover — and a call, a travel or a technical stoppage logs straight away with no team (`CALL_MADE`/`TRAVEL`'s `team` and `PendingCall.team` are optional for exactly this). On: `CallTeamDialog`/`TravelTeamDialog`/`StoppageDialog`'s technical step all ask which team, same as `StoppageDialog`'s injury step already did. A specific _player_ (goal, assist, turnover, injury) is a further, independent question that only has an answer once the roster below is also filled in — turning the flag on with no roster still gets you team-level attribution everywhere, just no player pickers. Any UI that names the team of a call has a **second wording** for the untracked case rather than a "no team" placeholder — `now_callPendingNoTeam` and a `say_call*NoTeam` per call kind, picked off `pendingCall.team` in `statusKey` and the `SAY` lookup. (`callPendingNoTeam` was the third, and went with the resolution row's heading — see above.) "Foul — No team" read like the name of a team; "Foul" is the same call-out minus an attribution nobody asked for. `btnNoTeam` survives only as what it always was: the skip button in `StoppageDialog`'s team step. Consequently `assistVars`' `team` falls straight through to the timeout/possession/pull chain when a call has no team — nothing renders it for such a call.

- **Whether Turn stops to ask who was involved is its own setting, and it is off by default** (`config.trackTurnoverPlayers`, "Ask who turned it over", under Statistics on the setup screen). A turnover is the most frequent thing on the action row, and two player pickers per tap is more than most volunteers can follow at pace — the count badge, the possession rule and every team stat work without it, so the default records the turnover on the tap and gives the row back. `turnoverPlayersTracked` is the guard `GameScreen.tryTurnover` reads, and it is deliberately the setting **and** a mode with a roster: `game` and `none` have nobody to ask about, so the flag can be left set while the mode changes on the config screen without meaning anything there (which is why the checkbox only renders for `team`/`player`). The setting is not a template field (like `statsMode`/`trackedTeam`, it is per-game), and `LogEditDialog` is untouched by it — attaching players to a turnover afterwards is a correction, and corrections stay available whatever the game was set up to ask at the time. `migrateStoredConfig` defaults it to **`true`** for a config stored without it: before it existed a rostered game always asked, and a reload mid-game must not change what that game does halfway through.

### GameContext owns all side effects

`src/state/GameContext.tsx` is where impurity lives: the 1 s `TICK` heartbeat, the whistle sequences (45/60/75 s pull, timeout end, cap), the delayed next-ratio reveal, the assistance-message queue (see i18n below), the `beforeunload` guard, and localStorage persistence. If you're adding time- or audio-driven behaviour, it belongs here, driven by derived values from state — not inside the reducer.

### The header menu, and the setup dialog behind it

The header's left slot used to be one button carrying three destinations at once — back to setup, end game, open report — distinguished only by its glyph, so what it did was legible only after pressing it. It is now `MenuIcon` in every status, opening `GameMenuDialog`: the same leave row (still named per status, still stopping at `ConfirmEndGameDialog` when it ends a game), plus the two things that had no door during a game at all.

- **`GameSetupDialog` is a pure read of `state.config`.** It answers what the dashboard can't when a captain asks: who received the first pull, which ratio the game started on, how long a timeout is. The coin toss is the sharp end — `startingOffense`/`startingSide`/`startingRatio` are entered once, consumed by `createInitialState`, and were never shown again anywhere. Because it only reads, it is the one dialog on this screen with no guard: there is no status in which looking at the rules is wrong. Field number and team names are deliberately absent (header, score panels). Three of its sections have a second wording rather than an empty value: **Rule B has no starting ratio at all** (`state.ratio` is null all game and the chip never appears), so the rule sentence is the answer; a game with no timeouts says so instead of showing a zero budget; and a `cappedTarget` gets a note, because the header chip shows the target in force and the dialog would otherwise quietly contradict it. Only the _automatic_ water breaks are configuration, so the section follows `waterBreaks.enabled` — a manual one is always available from the raised hand (`canWaterBreak`).
- **The layers peel off the one back guard, innermost first.** `GameScreen`'s `useBackGuard(true, …)` now closes the guide, then the setup dialog, then the menu, each with `stay()`, before a press means "leave the game". This is deliberately not a second `useBackGuard`: both hooks attach their own `popstate` listener on `window`, so each would answer the other's press.
- Labels are shared with the setup form wherever they exist (`coinToss`, `winConditions`, `startingOffense`, …); the `setup*` keys are only the values it has to write out as sentences. Rows are uppercased like `fieldLabel`, which is also what keeps the dictionary's inconsistent casing (`'TIME (Minutes)'`) from showing. Breaks are the exception to the sharing: they are stored in seconds because that is what the timers count, but a local `formatDuration` renders them as `45''` / `1' 15''` / `3'` — deliberately not `formatClock`, which is the zero-padded mm:ss of a clock that is _ticking_ — so those rows use `setupBreak`/`setupDuration` rather than the form's labels, whose `(seconds)` belongs to its inputs.

### The guide is a screen, not a dialog

`GuideScreen.tsx` is the walkthrough reached from the link under the tagline on the config screen **and from the game's header menu** — the second door matters, because until it existed the walkthrough written for a volunteer who has never seen Ultimate was unreachable by the volunteer who is mid-game and discovering they need it. It is rendered _by_ its caller (early return, not a `phase`), so the setup form — or the dashboard — stays mounted underneath and survives the round trip, and the reducer stays free of a UI-only state. Nothing about the game pauses for it: the clock, the whistles and the assistance queue all live in `GameContext`, above both callers. Its own back button is worded neutrally (`guideBackShort`) for exactly that reason — "Setup" was a lie from one of the two doors. Its text is ordinary `guide*` dictionary keys, so it translates like everything else.

The figures are real screenshots (`public/guide/*.png`), captured English-only by `scripts/guide-screenshots.mjs`, which drives an actual game through Playwright. The numbered pointers are **not** drawn into the images: the script measures the live bounding boxes and prints the `FIG_*` percentage arrays that `GuideScreen` positions markers with, and the captions are the translated list beside the picture. So after a layout change to the config screen, the dashboard or the report, re-run the script and paste the arrays back — otherwise the markers drift off their controls.

### A roster can be pasted or picked, and both are one parser

At a tournament the same two rosters get typed into a dozen phones from a list that already exists — a spreadsheet, a WhatsApp message, a text file the organiser sent. `RosterImportDialog` (setup screen only, one per team, opened from `PlayerRosterEditor`'s optional `onImport`) takes that list, and `src/state/rosterImport.ts` is the pure half that reads it.

- **The file picker fills the paste box; it is not a second path.** `FileReader` drops the file's text into the same textarea, so what gets parsed is always what the volunteer can see and edit — which is also why the file has to be **plain text in the box's own format**, and why CSV and JSON are refused rather than parsed. `accept` on the input is only a hint (Android pickers hand back whatever was tapped), so `isTextRosterFile` re-checks name and type and the dialog explains the refusal instead of turning a spreadsheet into nonsense players. `FileReader` rather than `file.text()` is deliberate too: it exists on older iOS Safari _and_ in jsdom, so the file path is tested rather than trusted.
- **`parseRoster` is forgiving within that one format, and honest about the rest.** One player per line, in any of the shapes a human writes: `12 John Doe`, `John Doe #12`, `12. John Doe`, a bare name, or **a bare number** — the roster editor accepts either half alone, so the parser must too (a number with no name is most of what a scorekeeper can see from the sideline). A tab-separated spreadsheet paste falls out for free, since a tab is whitespace. Unreadable lines come back as a `skipped` count, never an exception: the preview is the last validation step, and a paste that half-worked is more use than one that was refused.
- **Nothing is applied until the preview has been read**, which is also why the dialog can afford to guess. Appending skips players already there (same number and name — the roster editor's own duplicate rule), so importing the same list twice is harmless; the replace checkbox is the only way to lose what is already typed.
- **It goes through `ConfigScreen`'s `setPlayers`**, so importing into a saved team updates that team's stored roster exactly as adding a player by hand does.
- **There is no mid-game import** (`PlayersDialog` passes no `onImport`): once the game is running the roster is referenced by log entries, and a bulk replace would orphan them.

### Lines belong to the tracked team, and nothing carries over

Who was actually on the field for each point — so the report can answer who played most, whose points were held and whose were broken. `src/state/lines.ts` is the pure half (composition, the split a line is checked against, saved-line resolution); the reducer owns the record; `LineDialog` is the one place a line is entered.

- **`lineTrackingEnabled(config)` is the single gate, and no consumer reads `config.lines.enabled` directly.** It is `enabled && statsMode === 'team' && trackedTeam !== null`: line tracking follows the one roster Team mode watches, so `LineConfig` carries **no team of its own** and the line team is always `trackedTeam`. Its settings live in the config screen's **Statistics** section, under "Ask who turned it over", rather than in a section of their own — it is another thing this game tracks. Deriving it means moving the stats mode away from `team` retires the feature on its own — nothing has to reach in and clear the settings, and moving back restores what the user chose. It is also **off by default**, which is the safety net for the whole feature: with it off no point carries a `line`, every new `PlayerStatLine` field is zero, the report grows no pills and the card keeps its old columns. A test in the suite that needs changing means something leaked past the gate.
- **A check never refuses.** `lineIssues` reports `'size'`/`'ratio'` and the dialog warns in amber; an off-spec line still saves, on a second confirming tap (`data-line-save` goes `ready` → `warned` → `armed`). Outside professional play a team cannot always keep the ratio, and an app that insisted would simply be holding data it doesn't have. Unmarked players are counted but **never faulted** — three of seven unmarked makes the split unknown, not wrong, and faulting it would train the volunteer to tap straight through the warning.
- **A registered line is what the player pickers offer, and nothing else.** `playersOnField` narrows scorer/assist, turnover and injury to whoever was on the field. Three things about it: the fallback to the **whole roster** when there is nothing to narrow by (tracking off, the untracked team, a point with no line, or a line whose players have all left the roster) is load-bearing — restricting to nobody would leave the volunteer who skipped the line unable to attribute anything. The **goal dialog reads `points[last].line`, not `state.line`**, because `GOAL` has already moved the live line on to the next point by the time it opens. And **a player a substitution took off is dropped everywhere**: turnover and injury read `state.line` (who is out there now) and the goal dialog filters the finished point through `onFieldIds`, because a replaced player cannot have gone on to score it. Where the picker is narrowed, the inline "add a player" editor is replaced by a note — a name added there could not be offered, which reads as it being swallowed.
- **`LogEditDialog` is not narrowed, and that is why `onField` is a prop rather than something `InjuryAttributionDialog` reads itself.** A correction is made later and may be about a point several ago, whose line was a different seven from whoever is on now; narrowing there would hide the very player being named. Same reasoning as `trackTurnoverPlayers` leaving the log editor alone.
- **An injury asks who is coming on** (`InjurySubDialog`), because it is the one stoppage that routinely changes the line mid-point and the app only knows if it asks. Offered only when a named player was actually on the field. The stoppage is dispatched **before** the question, so skipping never loses the injury, and skipping is a real answer (a player who walks it off). Unlike `LineDialog`'s manual toggle it **keeps `lineName`**: D1 still played that point, one injury notwithstanding, where a hand-edited selection is a deliberately different line.
- **`replacementsFor` is narrower than the bench: in mixed you cannot swap an MMP for an FMP.** The line has to come back to the same split, so only matching markings are offered — otherwise the volunteer builds a line that could not have taken the field. Outside mixed the whole bench is fair game. Two softenings follow the "a missing marking is unknown, not wrong" rule: an **unmarked injured player** constrains nothing, and an **unmarked substitute** is always offered, since excluding them would hide a valid sub from a partly-marked roster. An empty result is **stated and closed** rather than dropped — the dialog says why and the injured player plays on — and the wording distinguishes "everyone is already on" from "nobody with that marking is left", which are different facts about the squad.
- **`LinePlayer.sub`/`off` are about _when_, never _whether_.** Both halves of a swap stay in `pointLine`, so a player replaced mid-point still played it and still counts in every stat; `off` exists purely so the pickers stop offering them. Coming back on clears it again. Consequently `SET_LINE` **replaces** `pointLine` while the disc is dead and **merges** into it once live: between points nobody has taken the field yet, so a player pencilled in and then taken out never played and must not be recorded as having done so.
- **`sub: true` is set only when `status === 'live'` and `pointLine` is already non-empty.** A change between points is the line for the point, and a first registration made late — the volunteer catching up mid-point — is not seven substitutions. `line` is who is on right now; `pointLine` accumulates everyone who appeared and **keeps whoever came off**, because "was on the field for this point" is the question a `PointRecord` answers. `REMOVE_PLAYER` scrubs an id from all three lists (historical `PointRecord.line` entries are left dangling on purpose, exactly as goal attribution already is).
- **Nothing carries over a goal except `nextLine`.** In Ultimate the line changes nearly every point, so leaving the last one in force would silently credit the wrong seven. `PointRecord.line` is **absent rather than empty** when nothing was registered — that is what lets the report count unregistered points instead of claiming nobody played them. The append sits before every `finishGame` return in `GOAL`, so a game-winning point keeps its line.
- **`canSetLine` is deliberately blind to `playHalted`.** A substitution after an injury is the case the `sub` flag exists for, so the stoppage that brought the sub on must not be what closes the door; a timeout and half-time stay open for the same reason. It does not reuse `canRecordEvent`, and its `next` form is `live`-only — anywhere else, the gap the volunteer is standing in _is_ the next point.
- **It is open before the game starts, and that is the point.** `notStarted` and `awaitingStart` are the gap in which point one's line is decided, exactly as every later one is decided between points, so the prompt row and the Roster button both take it there — otherwise the first point was the one point nobody could register. Nothing in between disturbs it: `beginPlay` and `PULL_THROWN` both leave `line`/`pointLine` alone. Only `phase !== 'game'` (still on the setup screen) and `finished` close the guard.
- **The dialog holds one draft per mode, and Save commits every mode that was touched.** A single shared selection meant switching to "Next point" and back threw away the substitution just picked, which defeats the argument for one dialog with two modes rather than two doors. An untouched mode is not re-dispatched, so opening it to glance at the next line can't re-register the current one; any touched mode being off-spec arms the confirmation, since Save is about to commit both.
- **Two doors in, both existing surfaces.** The **Roster button** becomes a two-entry chooser (`PlayersDialog`'s `onOpenLine`) — it already narrows to `[trackedTeam]` in Team mode, so there is one roster in scope; with lines off it opens the editor directly as it always did. And a between-points **`LinePromptRow`**, which shares `StoppageResolutionRow`'s slot **above the clocks** rather than the action row's reserved one, because that slot holds "Pull thrown" — and, before kickoff, "Start game" — in exactly the statuses the prompt is needed in. It yields to an open stoppage, and it hides itself once `pointLine` is non-empty. No new `now_*` key: the cap hint already rides the ambient line and a second claimant would fight it.
- **A saved line stores `playerKeys`, not ids**, because `selectSavedTeam` re-mints every player id on load. The key is `playerKey` in `rosterImport.ts` — exported rather than duplicated, so the roster editor's duplicate rule and line resolution can never disagree about whether two rows are the same person. `PointRecord.lineName` records which named line played a point.
- **Lines are edited in two places, and `config.lines.saved` is the one working copy.** `SavedLinesEditor` sits in the config screen's **Roster** section, because a line is made of the roster and the two are settled together at a tournament; `LineDialog` names one mid-game, when the seven who play together are in front of you. `SavedLineDialog` is deliberately not `LineDialog` — it edits a `SavedLine` against a roster with no game to speak of, so it takes everything as props and reaches for no context. It checks against **no ratio** on purpose: a predefined line is not tied to a point, so `expectedSplit` yields nothing for `gameRatio`, while a _fixed_ split is point-independent and still checked. An empty name is the one real block there — a line with no name could never be picked again — where the composition, as everywhere, only warns.
- **`setSavedLines` is exactly `setPlayers`' bargain**: the edit always lands in `cfg`, and is written through to the store only for a team already in it. A team named for the first time on this screen keeps its lines locally until `addSavedTeam` or the kickoff sync stores it — which is why `GameContext`'s sync passes `lines` for the line team. `setTrackedTeam` reloads the list from the store when the pointer moves, since `cfg.lines.saved` holds one team's lines and Ravens' must not follow the pointer onto Foxes.
- **`saveTeam` preserves `lines` when the incoming team omits the field.** It replaces everything else wholesale, and the roster sync writes that record with no lines for the team that isn't tracked — so without this a predefined line would be deleted the moment a game started. An explicit list (including `[]`, which is how the last one is deleted) still replaces. `saveTeamLines` is the narrow writer.
- **`config.lineSize` is not part of `LineConfig`, and that is deliberate.** How many players take the field is a property of the **field format** — sevens on grass, fives on beach — not of what this game chooses to record, so it sits out with the other rules and **rides the template** (`GRASS_TEMPLATE` sets 7, `BEACH_TEMPLATE` 5). `lines` stays out of `TemplateSettings` with the rest of the statistics settings, so applying a template can never switch line tracking on or off, or wipe a team's predefined lines. Only line tracking reads `lineSize`, but the format is true whether or not anyone is recording lines.
- **Markings are a roster edit, offered everywhere and always.** `PlayerInfo.gender` is optional (a roster typed off a sideline list has none) and set from a three-state cycle button on the player's row — not in the add form, so there is one place a marking is set and the add form stays the three columns that fit a 360px phone. Every roster editor passes `onSetGender`, in every stats mode and whether or not line tracking is on: a marking is a fact about the player, and it rides `ConfigScreen`'s `setPlayers` into the saved team, where the next game may well be the one that reads it. That is the point — a squad's markings are typed once per tournament.
- **The importer reads a trailing MMP/FMP** (`splitGender` in `rosterImport.ts`), so `29 Xavi MMP`, `Xavi FMP` and `29 MMP` all arrive marked. It only counts as a marking when something else is on the line: a line that is **only** `MMP` is a player called MMP, because a marking with nobody attached is not a roster entry and someone whose name really is those three letters would otherwise vanish. The abbreviations are matched exactly rather than a leading `M`/`F` — "Xavi M" is a middle initial far more often than a marking — and the marking is not part of `playerKey`, so the same person marked differently in two rows is one duplicate rather than two players.

### The report leaves by two doors, and they carry different things

"Copy to clipboard" is the archive: the whole report as plain text, **the history as the report shows it included**, for a spreadsheet or an email. "Share as image" is the thing you send to the team chat, and it deliberately drops the log — a full history is pages long and illegible as a picture, so the card is the score, the team stats and the player stats, plus the field/date/duration line that only ever lived in the copied text.

**The report's history is not the log.** `reportLogEntries` (in `stats.ts`) drops the turnovers and the calls — `turnover`, `undoTurnover`, `call`, `callResolved`, `travel` — because in a tracked game those arrive by the dozen and bury the shape of it: the goals, the breaks, the caps, the stoppages. Stoppages and SOTG stay, being neither a call nor routine, and `undoTurnover` goes with the turnovers it corrects rather than announcing a fix to something the reader never saw. The full thing is one tap away in `FullLogDialog`, read-only (editing a log entry is fixing a mis-tap in a game still being played — that door is `GameLog`, during the game), with its own copy button carrying **only** the log plus a two-line "which game is this" header. So the panel, the report's copy button and the dialog's copy button line up two-and-one: what you read in the panel is what the report's copy gives you (`visibleLog` feeds both, deliberately), and the dialog is where everything else still is. `logTextLines` is shared by both copy buttons so an entry can't print differently in the two, and `GameLogTable`'s `entries` prop is what narrows the table without narrowing where a row's detail is read from (still `state.log`).

The card is **drawn by hand onto a canvas**, not rasterised from the DOM. The app has no runtime dependencies and works offline off a service worker; every DOM-to-image library has to re-fetch the cross-origin Google Fonts stylesheet and inline it, which is exactly what fails on a pitch with no signal — silently, in the fallback font. `fillText` uses the faces the page already loaded. The split is `state/reportCard.ts` (pure: `reportCardModel` freezes everything into translated, formatted strings, and is unit-tested) and `components/reportCardImage.ts` (mechanical: measures and paints, untested by design). `teamStatRows` is shared with the on-screen table so the two can't drift, and `playerStatsTeams` decides which rosters both of them read.

Two things there are easy to undo by accident:

- **The image is rendered on mount, and `share()` is not an async function** (`hooks/useReportImage.ts`). A browser only honours `navigator.share` while the tap's user activation is alive, and on Safari even awaiting an already-resolved promise can spend it — so the fast path calls `navigator.share` synchronously inside the click and handles the returned promise afterwards. Making `share` async again, or moving the canvas render into the handler, silently demotes every phone to the download fallback; a test asserts the call has happened by the time `click()` returns. `canShare` missing (rather than returning false) is treated as "worth trying", since some browsers ship `share()` without it.
- **Web Share needs a secure context.** It does not exist over plain `http://` on a LAN address, so a phone pointed at `yarn dev` always downloads while the deployed HTTPS site shares. Nothing in the code can change that — check the deployed build before concluding sharing is broken.
- **A dismissed share sheet is not a failure.** `AbortError` goes back to idle; anything else falls through to downloading the PNG, which is also the path for every browser without file sharing. Downloading on cancel would force through exactly what was just declined.

`setupTests.ts` stubs `getContext`/`toBlob` to null — jsdom logs a "Not implemented" trace otherwise, and null is already what `drawReportCard` treats as "no canvas here".

**Naming a player is optional, so the player table has to account for the goals nobody was named on.** `playerStatLines` appends one aggregate line per team — labelled `unassignedPlayers`, flagged `unassigned`, `playerId: ''` — counting goals with no `scorerId`, goals with no `assistId` and turnovers with no `turnoverId`, pinned below the sorted players rather than sorted among them. Without it the columns quietly fail to add up to the score and the report reads as if those goals never happened. Four things hold it together:

- **A Callahan is not an unrecorded assist.** A goal caught in the endzone off the opposition's throw has no assist by the rules, so `LogEntry.callahan` (mirrored onto `PointRecord`) is what tells "nobody threw it" apart from "nobody typed it", and the aggregate skips it. It is written by a checkbox — `CallahanToggle`, shared by `AssistGoalDialog` and the log editor's `goalPlayers` branch — which **replaces the assist picker rather than disabling it**: the question has been answered, and a live row of chips that does nothing invites a tap. Both the reducer paths (`SET_GOAL_PLAYERS` and `EDIT_LOG_ENTRY`) clear `assistId` when it is set, so the flag and an assist can never both be on one entry. It renders in the log through `goalPlayersDetail`, where it takes the assist's place in the list for the same reason.
- **It is per team**, because Player mode lists both rosters behind a team filter and a combined line could sit in neither half of it. In Team mode there is only one team listed, so it collapses to a single row on its own.
- **It never appears alone.** `playerStatLines` returns `[]` when no player was named anywhere, because all three callers hide the section on an empty result and a table whose only row is "Not recorded: 12" says nothing the score doesn't. So the aggregate must not be the thing that makes the list non-empty.
- **`playerStatLines` takes `t`** for that label — it is the one line in the table whose text isn't a roster name. All three consumers (the screen, the copied text, the card) already had a `t` in scope, and translating in one place is what keeps them from disagreeing. The card dims the whole row including its total, which otherwise reads in `signal` like a player's tally; the screen dims and italicises it.

**Playing and Possession add two more views rather than more columns, each gated on its own data rather than both on line tracking.** `PlayerStatsTable` is props-driven (lines, columns, optional team dot, optional sub-label) and owns no state, so the screen hands it one of the three column sets in `playerStatColumns.ts` — Scoring (unchanged: Assists/Goals/Total), Playing (Pts/O/D/Won/Lost/Break ch.), Possession (Turns/D) — behind pills built from the same `pillClass` the team filter uses. Playing's columns all come off `PointRecord.line`, so it needs line tracking; Possession's come off the log's `turnoverId`/`defenseId`, so it needs only `trackTurnoverPlayers` (`turnoverPlayersTracked`) and nothing about a line at all — a Player-mode game that asks who turned it over but never tracks a line gets Possession with no Playing. `availableViews` (`ReportScreen`) and the equivalent `showPlaying`/`showPossession` pair (`reportCardModel`) are the one gate each reads; a pill (and the plain-text archive's column list) is offered only for a view with real data, and the row itself stays hidden when Scoring is the only one, since one tab onto the columns already on screen says nothing. **Possession's gate is `turnoverPlayersTracked(config) || playerLines.some(...)` on actual `turns`/`defenses`, not the flag alone**, because `LogEditDialog` can attribute a turnover as a correction whatever the flag says at the time (the same rule that leaves the log editor unnarrowed elsewhere) — a game that never turned the flag on, or turned it on after the fact, still surfaces the view the moment a turn or a D is actually named. Playing has no equivalent fallback: `canSetLine` itself refuses without `lineTrackingEnabled`, so `PointRecord.line` cannot exist unless the flag was on at the time, and there is nothing to retroactively notice. Because Possession no longer implies line tracking, it — unlike Playing — can now sit above the team filter in Player mode. The shared image is the exception to the "views, not columns" rule — see the card bullets below. Things to know about it:

- **`sortPlayerStatLines(lines, view)` pins the aggregate last itself**, rather than leaving that to `playerStatLines`. The report re-sorts a list that already contains it on every view switch, so pinning in the caller would let it shuffle back into the middle. Each view ranks by the column it is about — a Defence view ordered by goals answers a different question than the pill just asked.
- **The aggregate's per-player cells are dashes, not zeroes** (`aggregate` on the column). A zero there reads as a fact about someone, and the row is the one that knows nothing about anyone. `colPointsPlayed` and `colTurns` are the exceptions: the points nobody registered and the turnovers nobody was named on are exactly what keeps those columns adding up to the game.
- **A dash also means "never asked", which is the other way a zero would lie.** `PlayerStatColumn.unknown` is that second dash rule, and `colTurns` is its one user: a team that turned the disc over with no turnover ever attributed (`trackTurnoverPlayers` off, most often) gets dashes down the whole column rather than a roster of zeroes reading as a team that never lost it. `PlayerStatLine.turnsRecorded` is the fact, derived from the log and not the config — a correction made in `LogEditDialog` turns the column back on by itself. **No turnovers at all is recorded, not unknown**: nobody lost it, and zero is the answer. The aggregate always carries `turnsRecorded: true`, because its own figure — the unattributed ones — is precisely what the players are missing, and it is the one row that can state it.
- **The inclusion test widens to `goals || assists || pointsPlayed || turns`**, so someone who took ten points without scoring gets a row — which is most of who a coach is looking for.
- **Won and Lost replaced a single net `+/-` column.** Both read `PlayerStatLine.holds`/`.breaks` (won = the two added, lost = points played minus the two), which the field itself still carries — `sortPlayerStatLines`'s `playing` ranking still breaks ties on the underlying `plusMinus`, it is just no longer a column anyone sees, since Won and Lost already say everything it did.
- **The Possession view follows the disc rather than one team's half of it**, which is why `defenses` is read off the _other_ roster: one `turnover` entry carries `turnoverId` for the side that lost the disc and `defenseId` for the side that took it, so the two halves of the view come from the same entries counted in opposite directions. `sortPlayerStatLines` ranks it by **`defenses`**, not by its first column (`colTurns`): sorted by Turns the table would be a leaderboard of whoever lost the disc most; break chances stays the fallback tiebreaker even though it is no longer one of this view's own columns, since it is still a fair "who saw the most defensive looks" reading. It is the one view whose heading collides with another's: `colDPoints` ("D", points played on defence) and `colDefenses` ("D", turnovers forced) sit in the same card table under different group labels.
- **The card's player table is N columns driven by `playerHeader`**, and with either view active it carries **every** column the screen hides behind its pills — an image landing in a chat cannot be tapped through, which is the whole reason the screen splits them. `playerGroups` labels the runs (Playing / Scoring / Possession — Playing first when present, since points played is the question the whole line-tracking feature was added to answer — with vertical rules and spans that must cover the numeric columns exactly), built only from whichever of Playing/Possession this game actually has. Only `colTotal` is dropped, being arithmetic sitting next to Goals and Assists, and it is dropped whenever anything is grouped in, not only when Playing is. With neither view available the card is unchanged: three scoring columns, `playerGroups: null`, and no group row repeating the section title. `playerAccent` names the amber column by index — 0 (points played) when Playing is present, otherwise the last column, which is Total in the ungrouped case and Possession's `D` when Possession is the only extra view, neither of which is "anybody's headline figure" but both of which are cheap, defensible defaults rather than a real design statement. The cells go through the screen's own `playerStatColumns`/`statCellText`, so the card cannot disagree with the table about a figure, dashes included. The copied text is the archive and carries every _available_ view's columns on one line per player, plus the named lines each player appeared in (`linesSummary`).
- **The drawer measures the columns rather than spacing them evenly, and the card grows wider rather than dropping one** — the same bargain the ledger already strikes. Headings run from "O" to "Break ch.", so an even split would either ellipsise the long ones or spend the width on the short ones; each column takes its widest heading-or-cell plus a gutter. The name column asks for its longest name too, between `NAME_MIN` and `NAME_MAX`, past which one three-barrelled name would drag the whole card out of shape and an ellipsis is the lesser evil.

### i18n key conventions

`src/i18n/{en,es}.ts` are plain objects; `es` is typed as `typeof en`, so **a key missing from Spanish is a type error**. Three conventions are load-bearing:

- `state.assist` is a bare key string set by the reducer. It is **not** rendered directly — `src/state/assistOccurrence.ts` looks it up in its `SAY` map to decide whether there is anything to shout.
- `canScore`/`canUndo` reasons render as `assist_blocked_<reason>` (the only surviving `assist_*` keys; they are flashed on the score panels, not in the bar).
- The bar shows one of two things, and the distinction is the whole point of the copy:
  - **`say_*` (green)** — the verbatim words to shout, quoted, with a speech icon. Transient: 7 s (4 s if it waited — see the queue below), then it gives way. An assist key absent from `SAY` has nothing to announce (turnover, disc-in-play, a logged injury are bookkeeping) and never takes over the bar.
  - **`now_*` (amber)** — the standing "what's happening and what do I do", derived from `state.status` rather than from `assist`, which is why it is always available as the fallback.
- The hand signal to _make_ is a third concern: `assistOccurrence` maps a subset of assist keys → official WFDF pictograms in `public/signals/*.png`. A key with no mapping renders no picture — many messages are announced but never hand-signalled. So a new assist key means deciding, separately, whether it needs a call-out and whether it needs a signal.
- Player calls set `assist` to `call_<kind>` when made and `resolution_<outcome>` when resolved; these appear in **both** the `SAY` map (green call-out) and the `SIGNAL` map (a signal per infraction and per outcome). Stall-out has no dedicated WFDF pictogram, so it borrows `timing.png`. Log-only detail for the two call entry types is built by `callDetail` in `stats.ts` (alongside `goalPlayersDetail`/`turnoverPlayersDetail`), used by both the log table and the plain-text report.
- `SignalCard` is a dialog floating over the bottom-left of the score panels. It is `pointer-events-none` so it can never swallow a goal tap on the panel underneath. It renders no state of its own: which picture and for how long is the queue's answer, the same one the bar renders words from.

#### Messages queue; they no longer overwrite each other

The call-out and the signal used to be two independent transients, each keyed off current state, so **the newest event simply replaced whatever was on screen** — a call-out three seconds into its seven was gone unheard. `src/hooks/useAssistQueue.ts` (owned by `GameContext`, exposed through `AssistCtx`/`useAssist`) now holds one active message and a queue of at most 2 behind it; `src/state/assistOccurrence.ts` is the pure half that decides what is worth showing.

- **One occurrence carries both halves.** `nextOccurrence` reads `state.assist` and `currentWhistle` _together_, so an assist and a whistle landing in the same update (the game-on blast and "Game on!") come out as a single item. Split in two they would queue against each other and the words would arrive four seconds after the sign. Whistle art still wins over the assist's own signal. The assist half is keyed `assist:nextLogId:ratioSignalId` — `nextLogId` so two goals in a row are two occurrences, `ratioSignalId` so re-tapping the ratio chip re-arms one.
- **Only the tier preempts.** 2 = safety and game-state (injury, technical, SOTG, caps, game over), 1 = an infraction or open dispute (the seven calls, travel, the resolutions) and every whistle, 0 = everything else. Higher tier takes the screen immediately and pushes what it interrupted back to the **front** of the queue rather than dropping it; same tier always waits its turn.
- **`SUPERSEDES` is the one escape from queueing.** `nextRatio` replaces `goalScored` outright, because the ratio reveal is already held back 3 s by `GameContext` precisely so it lands while the goal sign is up — queueing it would undo a stagger that was deliberately timed. Nothing else belongs in that map without the same argument.
- **`STILL_RELEVANT` is checked at dequeue, never mid-display.** A queued `call_*` whose `pendingCall` is gone is dropped silently — announcing a call that has already been resolved reads as a bug. Pulling words off the bar half-read would be worse than letting them finish, so an active message is never re-examined.
- **None of this touches the clocks.** `pendingCall.elapsedSeconds`, the pull count, the two-minute stoppage rule and the whistle _audio_ all run off `TICK` in the reducer regardless of what is displayed. The visible consequence is that a queued call-out can briefly describe a moment the game has already left, which is why an occurrence freezes its own `vars`/`kindKey`/`halfSideKey` at build time instead of reading live state at render — the ambient `now_*` line, being about right now, still reads live state.

Interpolation is `{name}` placeholders via `t(key, vars)`. Add a language by copying `es.ts`, registering it in `dicts`, and extending `detectLang` in `src/i18n/index.tsx`.

The action row's `lbl*` keys are the exception to translating everything: they are English in all three dictionaries on purpose. They have to fit ~7 characters at 9 px, Ultimate vocabulary is English on Spanish and Catalan fields anyway, and identical strings keep the button widths identical across languages. The full wording still translates — it is the `aria-label`/`title`, which is what a screen reader and a long-press tooltip read.

### The dashboard action row

`ActionButton` in `GameScreen` is a glyph plus a **micro-label**: a 9 px uppercase word small enough to read as part of the icon rather than as a caption. It stacks the two differently per orientation, and the reason is easy to get backwards: `lscape:` is capped on **height**, not width, so landscape has _more_ horizontal room per button (~160 px vs ~60 px at 360 px portrait) and less vertical. Portrait puts the label under the glyph; landscape puts it beside, spending the free axis and costing the row no height. Icon-only is not the landscape answer.

The stoppage button is the one with no visible label — no single short word covers injury, technical and SOTG without misleading — so it carries its meaning in `aria-label` alone. Glyphs live in `src/components/icons.tsx` and share one drawing spec (24 viewBox, no fill, 1.5 stroke, round caps); an icon that departs from it looks pasted in.

The row is deliberately capped at five: line tracking got no button of its own but went behind Roster instead (see the lines section above), because a sixth would not fit a 360 px phone.

`ActionButton`'s optional `badge` is used by Turn alone, and shows `pointTurnovers` from 1 upward (`9+` past nine, so the disc keeps one size). Its real job is not the count: when the disc goes back to a team that has already held it this point, the possession rule returns to a half it has been on before and **nothing else on screen moves**, so without the badge a registered turnover looks like nothing happened. It sits _inside_ the button's top-right border rather than straddling it the way a notification badge usually does — these buttons are ~60 px wide with a couple of pixels between them, so anything hanging outside eats that gap and rides the `active:scale-95`. It is left inside `disabled`'s fade on purpose (a count still true but not actionable), and it is `aria-hidden`: the button's `aria-label` is authoritative, and the count deliberately stays out of it.

**`useLongPress` fires its tap on `click`, never on `pointerup`, and that is load-bearing.** On a touch screen the compatibility `click` after a release is hit-tested against the DOM _as it is then_, so a tap that opened a dialog on `pointerup` had its own click delivered to whatever the dialog had just put under the finger. It bit exactly here: Turn is the rightmost button in the row and `Modal` is a bottom sheet on mobile, so the sheet's Save button overlapped the bottom ~7 px of Turn — a low thumb recorded the turnover with nobody attributed and dismissed `TurnoverDialog` before it could be read, intermittently, because `AssistanceBar` grows a line and moves the row. Firing on `click` puts the handler after the event instead of before it, which is why every button on the row _without_ a hold was already immune. `Modal` guards the same ghost click for the backdrop (`pressedBackdrop`) — that guard covers only the backdrop, and cannot be widened to the panel without breaking keyboard activation, which is a click with no pointerdown. Two things fall out of it: a press that ends off the element no longer fires (implicit pointer capture had been delivering `pointerup` to the original target regardless, so the documented "movement cancels the press" only became true for touch here), and these buttons stop being pointer-only. One consequence is pre-existing and shared with the whole row: `active:scale-95` shrinks the hit box along with the picture, so the outer ~1 px rim of an action button is tap-dead while pressed.

Timeouts are absolutely positioned over the score panels rather than nested inside them: `ScorePanel` is itself a `<button>`. Unlike `SignalCard` they are _not_ `pointer-events-none` — they are real controls, which is why they stay small and hug the outer top corner, away from where a thumb goes for the score.

### Styling

Tailwind with a custom dark palette (`pitch`, `panel`, `line`, `chalk`, `signal`) and a custom `lscape:` screen — `(orientation: landscape) and (max-height: 500px)` — for phones held sideways, which needs its own compacted `GameScreen` layout. Shared class strings live in `src/components/ui.ts`; reuse them rather than re-deriving button/input classes.

The UI target is a volunteer who has never seen Ultimate, one-handed on a phone in sunlight: huge tap targets, tap = +1, long-press = undo (`src/hooks/useLongPress.ts`).
